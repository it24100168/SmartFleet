# Local performance sample — 5 October 2026

The [repeatable read-only script](../../scripts/performance-assessment.mjs) ran against the **local PostgreSQL** assessment API at `http://localhost:5078`; [raw JSON output](performance-local-2026-10-05.json) contains the measured values. The script authenticated as a local demo Supervisor without writing credentials into the report, then sent 30 requests per endpoint using five concurrent workers. Every request had a 10-second timeout. Percentiles use nearest-rank over client-observed HTTP latency.

| Endpoint | Success / total | p50 | p95 | Maximum |
| --- | ---: | ---: | ---: | ---: |
| `/api/health` (DB connectivity) | 30 / 30 | 32.4 ms | 64.3 ms | 68.7 ms |
| `/api/rovers` (PostgreSQL list) | 30 / 30 | 11.7 ms | 647.7 ms | 648.7 ms |
| `/api/workflows/fleet` (PostgreSQL snapshot) | 30 / 30 | 20.6 ms | 56.1 ms | 56.7 ms |

The rover-list p95 includes a real high-latency sample; it has not been removed or replaced. These are HTTP observations from one workstation and local Docker database, **not** a cloud capacity guarantee or isolated SQL-query benchmark. No requests failed in this run. The script is read-only, so it does not measure concurrent dispatch writes or reservation contention; the PostgreSQL integration tests cover correctness of those cases separately.

The script also read persisted `AgentTiming` logs from workflow `b855bd3f-aa3d-43db-bf71-e0a9c1c85e4b`: Planner `GeneratePlan` 210 ms, Dispatch/Telemetry `SelectAndReserve` 67 ms, Safety Guard `EvaluateSafety` 66 ms, each attempt 1. No Maintenance call was present in that selected run. These are historic operation durations recorded by the application, not timings generated by this read-only load and not per-SQL-call durations.
